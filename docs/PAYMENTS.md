# Payment & Fee System Design

This document outlines the architecture, data models, and lifecycles for Phase 3 (Fees & Payments) using Razorpay.

## Official Documentation References
The following Razorpay documentation pages dictate the integration:
- Orders API: `https://razorpay.com/docs/api/orders/`
- Checkout & Signature Verification: `https://razorpay.com/docs/payments/server-integration/nodejs/payment-gateway/build-integration/`
- Webhooks (Events, Headers, Verification): `https://razorpay.com/docs/webhooks/`
- Payments Fetch API: `https://razorpay.com/docs/api/payments/`
- Refunds API: `https://razorpay.com/docs/api/refunds/`

## Data Model

- **FeePlan**: Master template for fees (e.g., Monthly Base Fee). Versioning is handled by setting `effective_to` on the old plan and creating a new one. Invoices snapshot the plan state; changing a plan never affects historical invoices.
- **Concession**: Discounts mapped to a student (e.g., 10% Sibling discount). Can be percentage or flat.
- **Invoice & InvoiceLine**: The actual bill. `Invoice` tracks the aggregate `total_paise`, `balance_paise`, etc. Lines track individual charges and tax.
- **Payment**: Tracks an intent to pay (Razorpay Order) and its final outcome (Captured/Failed).
- **PaymentEvent**: An append-only ledger of all webhooks and checkout events received from Razorpay to guarantee auditability and idempotency.
- **Allocation**: Joins `Payment` to `Invoice` to support partial payments and one payment covering multiple invoices.

## Lifecycles

### Invoice Lifecycle
1. **DRAFT**: Generated by Celery beat task prior to period start.
2. **ISSUED**: Finalized. Immutable except for payment fields and status.
3. **PARTIALLY_PAID**: Payment received but `balance_paise > 0`.
4. **PAID**: `balance_paise == 0`.
5. **OVERDUE**: Grace period passed without full payment. Late fees may be attached.
6. **CANCELLED**: Erroneous invoice voided before any payments were made.

### Payment Lifecycle
1. **CREATED**: User clicked "Pay". We created a Razorpay Order and returned the ID.
2. **PENDING**: User is completing the flow in Razorpay Checkout.
3. **CAPTURED**: Webhook `payment.captured` received. Allocation to invoices occurs here. Receipt is generated.
4. **FAILED**: Webhook `payment.failed` received.
5. **REFUNDED**: Admin initiated a refund.

## Numbering System
- **Invoices**: `PDN/FY2026-27/00001`
- **Receipts**: `PDN/RCPT/FY2026-27/00001`
*Implementation*: A dedicated `Counter` model generates these sequentially using `select_for_update()` inside the same database transaction that creates the invoice/receipt. This ensures zero gaps even if a transaction rolls back.

## Rounding Rules
- All money is stored in integer `paise`.
- **Rule**: `ROUND_HALF_UP` to the nearest integer paise.
- Applied precisely once per percentage calculation (e.g., tax calculation on a line, concession calculation on a line). 
- Totals are simple integer sums of the rounded lines: `Total = Sum(Line Subtotals) - Sum(Line Discounts) + Sum(Line Taxes) + Late Fee`.
- No floating-point math is allowed anywhere in the pipeline. `decimal.Decimal` will be used for intermediate rate math before conversion to `int`.

## Webhook Handling
The webhook is the absolute source of truth.
1. Read `request.body` strictly as raw bytes (do not parse JSON yet).
2. Compute HMAC SHA256 using `RAZORPAY_WEBHOOK_SECRET` and compare to `X-Razorpay-Signature` using `hmac.compare_digest`. Reject 400 on failure.
3. Check `X-Razorpay-Event-Id` against `PaymentEvent`. If exists, return 200 (idempotent replay).
4. Lock the corresponding `Payment` using `select_for_update()`.
5. Process state change, allocate funds to `Invoice`, and trigger receipt PDF generation.
6. Commit transaction and return 200.

## Reconciliation
A nightly Celery task fetches Orders and Payments from Razorpay modified in the last 48 hours. It checks our `Payment` table. If Razorpay reports `captured` but our database says `CREATED`/`PENDING`, it synthesizes the event and runs the exact same processing pipeline as the webhook (effectively catching dropped webhooks). A `ReconciliationReport` is logged for Admin review.

## Failure Modes
- **Client drops before Checkout success**: Order remains `CREATED`. Subsequent retry creates a *new* order/payment.
- **Webhook Missed**: Caught by Reconciliation task.
- **PDF Generation Fails**: The webhook transaction commits successfully. PDF generation is deferred to a Celery task with automatic retries.
- **Amount Mismatch**: Razorpay orders strictly enforce amounts. However, if a webhook payload amount differs from our expected order amount, the system will mark the Payment as `CAPTURED` (to reflect reality) but will flag it for Admin Review and will *not* auto-allocate.

## Decision Log
1. **Concessions & Late Fees**: Concessions apply to base fees *before* taxes. Late fees apply strictly *after* the fact to the outstanding balance and do not receive concessions.
2. **Partial Payments**: Supported at the data model level (`Allocation`), allowing Admin to enable custom-amount payments in the UI in the future.
3. **Overpayments**: If a payment exceeds the target invoice balance (e.g., manual offline entry), the excess is recorded as an unallocated `Payment` balance. An Admin can manually allocate it to future invoices.
4. **Refunds**: Executed purely by Admins. They trigger the Razorpay Refund API. The subsequent `refund.processed` webhook creates an `Adjustment` record (Credit Note) to increase the invoice balance (if reversing an allocation) or simply logs the refund if it was an unallocated overpayment.
